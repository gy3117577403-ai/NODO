# NODO 开发笔记

## Odoo 20 前端与样式

- Odoo 20 使用 OWL 3。阅读同版本组件后再写补丁，沿用 `signal`、`proxy`、`Plugin` 和 `useProps` 的写法。
- OWL 3 的 `t-model` 接收带 `.set()` 的 signal，例如 `t-model="this.note"` 对应 `note = signal("")`。绑定 `proxy` 成员的当前值会在渲染时抛错。
- OWL 3 会把 `t-call` 的子节点编译成延迟渲染的内容。在其中用 `t-set` 无法给被调用模板传变量，私聊标题曾因此拿不到已有的角色数据。用 `t-call-context` 显式传参。
- Odoo 20 的前端翻译优先按调用处模块取词。在 NODO 的 `.po` 里加已有的 `mail` 译词，不会替换其模块内的译文。群聊退群文案在原操作和确认框入口按群聊类型调整。
- 继承 QWeb 模板时，用稳定的 `name`、`id` 或绑定属性定位节点。可翻译的 `alt` 等属性不能用于 XPath。使用 `t-attf-class` 生成的动态类名无法用 `hasclass()` 匹配。
- QWeb 内联脚本里的 `&&` 和 `<` 可能被转义或被 XML 当作标签。脚本优先独立放在资源文件里。
- 讨论页不能自动打开最近对话。选中对话会触发原生已读处理。
- 颜色和阴影沿用 `primary_variables.scss` 的 `$nodo-*` 变量和 `nodo-pane`、`nodo-state` 等 mixin。

## 模型、数据和测试库

- Odoo 20 二进制字段读取的是 `BinaryValue`，内容取 `.content`。写入用 `odoo.tools.BinaryBytes`。
- 数据 XML 的 `<function>` 要调用带 `@api.model` 的模型方法。
- `noupdate` 跳过升级时对现存记录的更新。默认仍会创建缺少 XML ID 的记录。只允许首次安装创建的记录要同时设置 `forcecreate="0"`。用 `powershell -ExecutionPolicy Bypass -File scripts/nodo.ps1 test nodo_base` 在一次性数据库验证全新安装，开发库升级覆盖不到这类问题。
- `scripts/nodo.ps1 update` 失败可能使 Odoo 服务停在停止状态。修复后重新执行升级，确认 `http://127.0.0.1:8079/web/login` 返回 HTTP 200。
- `HttpCase` 请求附上 `?db=<库名>`，避免在开发库和一次性库同时存在时进入数据库选择页。
- 权限组用 `res.groups.privilege` 分类。系统参数用 `get_str`、`set_str`、`get_bool`、`set_bool`。

## PowerShell 5.1

- 含中文的 `.ps1` 文件用带 BOM 的 UTF-8 保存。
- 双引号 here-string 会展开 `$()`。传递原样文本时用单引号 here-string。通过管道送入容器的内容还要留意开头的 BOM。

## 讨论 Store 与群聊（T1）

- 找人结果以 `res.partner` 为聊天对象。原生多选建群通过每个联系人的 `main_user_id` 找用户，因此精简找人响应时也必须带上这条 Store 关系。私聊和群成员复用 `_store_partner_fields` 中的角色数据。
- Odoo 20 的 Store 可同时服务请求响应和总线推送。角色字段用 `internal=True` 跟随 Store 接收者的权限。读取已有成员的联系人时，即使记录用了 `sudo()`，门户和访客也不能收到角色字段。
- 一个联系人可以关联多个用户。按角色匹配时把账号启用、内部用户和组条件放在同一个 `user_ids` 的 `any` 条件内，避免把已停用账号的角色算给当前账号。`all_group_ids` 包含隐含组。
- 构造同一联系人下有在用和停用账号的用例时，先创建账号，再写 `active=False`。创建时直接传 `active=False` 会尝试归档联系人，触发上游对关联在用账号的限制。
- 默认群名由 Odoo 根据成员生成。改名、加人和退群沿用原生入口，添加人时复用原生的排除已有成员规则。
- 群聊初始 Store 可能只带生成默认群名所需的成员。打开成员面板后，其余成员会异步加载。浏览器验收先等待目标成员出现，再核对人数。
- 创建门户测试用户时显式传 `notification_type='email'`。NODO 的系统内通知默认值会碰到上游约束，只有内部用户允许使用 `inbox`。

## 频道（T2）

- 频道的 `group_ids` 是原生自动订阅组，`group_public_id` 是可访问频道的授权组。给用户增加组后 Odoo 自动补成员，取消角色不会自动退订。全员通知的发言组独立配置。
- 配置了自动订阅组的频道在原生会话菜单里只提供隐藏入口，频道列表仍有「离开」。隐藏后可能触发频道空状态，因此空状态写「没有可显示的频道」。
- 原生发布路由 `/mail/message/post` 会用 `sudo()` 调用业务记录的 `message_post`。`sudo()` 保留当前用户 ID，权限校验应检查实际用户及权限组。`env.is_system()` 会把 sudo 模式也当作管理员，频道管理使用 `env.user._is_system()`。
- `mail.message.create` 可以直接创建消息，消息目标也可能来自 `default_model` 和 `default_res_id`。服务端校验覆盖这条入口及原生 `message_post`。表情回应使用独立的读取权限。
- 原生 `is_readonly` 同时影响发言及其他频道操作。NODO 的发言名单独立控制，批准角色获得发言权后仍按原权限访问频道管理设置。
- 频道总线共享给多位成员，不能广播某个查看者的发言结果。改发言开关或名单时清除频道里的权限缓存，打开频道的客户端再通过 Store 获取自己的发言结果。
- 频道分栏、频道列表视图和 `Ctrl+K` 的讨论命令分别提供创建入口。按用户权限改变列表视图时，把权限条件加入 `_get_view_cache_key`，避免复用错误的架构。
- `mail.module_install_notification` 是上游欢迎记录。NODO 首次安装解除它与「全员通知」的关联，并保留记录和 XML ID。已安装的开发库历史只在用户确认后处理。

## 讨论单据卡片与分享（T3）

- `nodo_base` 提供 `nodo.discuss.record` 服务。销售实现放在 `nodo_base_sale`，当 `nodo_base` 与 `sale_management` 都装上后自动安装。角色组和单据应用的权限分别配置，卡片读取以应用现有访问权为准。
- `nodo_base_purchase` 以同样的扩展点接入标准 `purchase.order`，并继承 `purchase.purchase_order_form`。采购表单的「发到聊天」可选择已加入且可发言的「生产协调」。加入频道只提供会话权限，采购卡片的供应商、金额和状态仍按查看者的单据权限读取。已有开发库用 `scripts/nodo.ps1 install nodo_base_purchase` 安装衔接。
- Odoo 在安装依赖的流程中检查自动安装项。若两个依赖早已装好，后来才把衔接模块放进现有开发库，用 `scripts/nodo.ps1 install nodo_base_sale` 安装这次新增的衔接。
- `get_record_cards(references)` 每次接收最多 50 个 `{"model": "sale.order", "id": 1}` 这样的引用，按首次出现的顺序返回去重后的卡片。每项带 `model`、`id`、`title`、`subtitle`、`status`、`status_type`。无权限、已删除和无效的引用均省略。未声明的持久模型按读取权限返回模型名和 `display_name`。
- `get_record_card_types()` 列出当前用户拥有读取权限的已声明类型，字段为 `model` 和 `label`。实际选单据沿用 Odoo 的记录选择器和记录规则。
- `share_record(model, record_id, kind, target_id, note='')` 返回 `channel_id` 和 `message_id`。`kind='person'` 时用 `res.partner` 的编号，其余使用已加入的 `group` 或 `channel` 编号。调用时重新校验单据和发言权限，正文只写站内链接及附言。单号、客户、金额等信息由每位接收人按自己的权限读取。
- 原生私聊使用 `_get_or_create_chat`。分享使用 `message_post`，沿用讨论总线。除 NODO 的公告发言名单，还要遵守上游 `is_readonly` 和频道角色控制。选择列表中的权限结果仅用于展示。
- 讨论主视图和小窗都以会话编号挂载 `Thread`。卡片在本次挂载内合并请求，复用在途请求和 5 秒内的成功结果。重新打开会话从服务端读取当前状态；无结果的引用不留缓存。只替换成功显示卡片的对应链接。
- 单据金额使用 `odoo.tools.misc.format_amount` 处理当前用户语言和币种。销售状态文字取字段的 `_description_selection(env)`，颜色类型由销售衔接模块声明。

### 给一个已有模型接入

1. 让接入模块依赖 `nodo_base` 和这个模型所属的模块。在 `_nodo_card_models()` 中保留上游声明，并加一条模型与选择器名称的映射。
2. 在业务模型上实现单条记录的 `_nodo_discuss_card()`。返回 `title`，可加 `subtitle`、`status`、`status_type`。状态类型用 `warning`、`info`、`success` 或 `muted`。用当前记录环境读取业务字段，沿用它的字段和记录权限。
3. 给表单头部添加 `type="object"` 的「发到聊天」按钮，调用返回通用选择框的模型方法。下面以已经存在的 `example.document` 为例。

```python
from odoo import api, models


class DiscussRecord(models.AbstractModel):
    _inherit = 'nodo.discuss.record'

    @api.model
    def _nodo_card_models(self):
        return {**super()._nodo_card_models(), 'example.document': self.env._('工艺文件')}


class ExampleDocument(models.Model):
    _inherit = 'example.document'

    def _nodo_discuss_card(self):
        self.ensure_one()
        values = self.read(['display_name'], load=None)[0]
        return {'title': values['display_name']}

    def action_nodo_share_to_chat(self):
        return self.env['nodo.discuss.record']._share_action(self)
```

在已有表单视图的继承中加入按钮，并把视图列入接入模块的清单。

```xml
<xpath expr="//form/header" position="inside">
    <button name="action_nodo_share_to_chat" type="object"
            string="发到聊天" groups="base.group_user"/>
</xpath>
```

手动调用批量服务时，网页使用 ORM 的 `nodo.discuss.record.get_record_cards`；已有外部 API 身份的客户端可调用 `POST /json/2/nodo.discuss.record/get_record_cards`，在请求体里传 `references`。单个成功结果形如下面的卡片。

```json
{
  "model": "sale.order",
  "id": 1,
  "title": "报价单 S00001",
  "subtitle": "协作客户 · ¥1,000.00",
  "status": "报价单",
  "status_type": "warning"
}
```

## 讨论消息、回执与附件（T4）

- `nodo.discuss.recall_seconds` 默认 120 秒，修改后可重新打开会话，让 Store 按最新值下发编辑期限。`nodo.discuss.file_limit_mb` 默认 50，每 MB 按 1024² 字节计算。这两个值可在「设置 → 技术 → 系统参数」配置，服务器通过 `get_int` 读取。
- 编辑和撤回按消息的服务端 `create_date` 算时间。原生 `/mail/message/update_content` 用空正文及空附件列表表达删除。讨论里将这种调用并入撤回／管理员删除规则，直接修改正文、时间或删除行时也检查权限。
- 运行中的 Odoo ORM 会忽略对 `create_date` 等日志字段的普通写入。超时用例用 Odoo 的 `mock_datetime_and_now` 把当前时钟推进到期限之后。
- 撤回和管理员删除保留 `mail.message` 的 ID、发送时间和排序。写入占位文字后用原生消息内容更新和 Store 总线通知客户端。删除专属于该消息的附件文件。文件若也用于另一条消息或业务记录，解除这条消息的引用，保留其他位置的文件。
- Store 的 `from_method()` 校验方法名，使用 `_store_…_fields` 格式。消息扩展字段要同时加进常规消息查询和 `_store_message_update_extra_fields`，两个路径分别覆盖打开会话和实时更新。
- 已移除的图片访问 `/web/image` 时，原生路由可能返回 HTTP 200 和默认占位图。核对撤回后的文件失效时，查附件记录与 `/web/content` 原文件路由。
- 私聊回执复用 `hasSomeoneSeen` 和成员的原生已读指针。原生 `showSeenIndicator` 只有对方读过后才显示图标，所以讨论直接在自己最后一条可见消息后显示文字状态。群聊及频道沿用原有未读分隔线。
- 选文件、拖拽、粘贴都进入 `mail.attachment_upload`。讨论在启动 XHR 前按文件大小提示，上传路由在 pending 附件写入前校验原始字节数，ORM 还会对贴到消息上的附件做检查。
- Web 文件服务的 `FILE_UPLOAD_ADDED` 提供 XHR，进度来自 `xhr.upload` 的原生 `progress` 事件。保留原生取消上传与临时附件清理流程。
- 原生上传态会降低整张附件卡片的透明度，悬停层也会盖住上传状态。讨论将进度层置于悬停层上方，并仅淡化卡片内容，保留可读的百分比和取消按钮。
- 原生输入框的 Enter 处理已有 `isComposing` 保护，并支持 Shift + Enter。原生 @ 通过频道或讨论串成员返回候选，NODO 在原模板里接上角色 Store 字段。

## 讨论通知（T5）

- 原生消息页签标题统计弹出过的提醒，聚焦窗口会清空；原生讨论分栏主要按未读会话数统计，开启通知的提示也会占一项。NODO 用 `discuss.channel.member.message_unread_counter` 计消息条数，顶部、分栏和页签共用 Store 计数。初始化只下发当前内部用户可读会话的非零计数，完整加载会话后改用其原生成员计数和实时更新。页面聚焦本身不清除未读。
- 账号通知设置扩展 `res.users.settings._store_settings_fields`，同时进入打开页面时的 Store 和原生总线更新。首选项用可写关联字段，Odoo 20 允许普通用户编辑自己的字段需设 `user_writeable=True`，其它用户仍按记录规则限制。
- 原生每会话免打扰字段是 `discuss.channel.member.mute_until_dt`，关闭后由原生动作复原。原生网页提醒及 Web Push 对直接 @ 提及有例外。NODO 在网页提醒和推送接收者两处应用免打扰，原生消息总线和未读计数继续工作。
- 页面前台用原生右下角通知组件，后台沿用桌面通知和已有的 Web Push 订阅。服务端以通知设置过滤聊天推送，原生 Service Worker 仍负责关页后的显示和打开会话。消息预览以纯文本传递。
- 原生通知容器在桌面宽度下靠右上。聊天提醒保留同一个原生组件，只调整这类提示的位置。编译资源时 LibSass 会把小写 `min()` 当成 Sass 函数，混用尺寸和 `calc()` 会使整包样式编译失败。这里用 `width` 和 `max-width` 分别表达。
- 普通 HTTP 的截图粘贴走 `paste` 事件的 `clipboardData.files`，和受安全上下文限制的 `navigator.clipboard` 是两个入口。保持开发机回环绑定时，可用 Chrome 进程的 `--host-resolver-rules` 把专用域名映射至回环地址，核对浏览器处理普通 HTTP 的表现。详见 [聊天部署前提](聊天部署前提.md)。

## 采购协作权限

- Odoo 20 的 `ir.access` 合并权限和限制，查询及记录访问使用 `_access_domain`。采购单明细应用采购单的公司和记录范围，业务按钮另查个人权限及状态。避免使用已弃用的 `_check_access` 作为记录权限入口。
- 原生采购组会同时开放采购单、明细和分析。个人关闭查价须覆盖金额字段和基于独立 SQL 视图的采购分析，讨论卡片只读取当前查看者有权读的字段。导出测试需给隔离库账号明确授予原生「允许导出」，才能验证具体价格字段是否被拒绝。
- 菜单可见性原生按权限组共享缓存。采购协作两个菜单按当前员工重新判定，改基础查看时用 `env.transaction.invalidate_ormcache()` 清理菜单结果。改权限后刷新已打开的页面，重新装载对应字段。
- 原生视图服务把 `get_views` 存在磁盘缓存。个人查价权限变更后，采购单需要重新向服务端取视图及字段配置，避免旧表单请求已经收回的金额字段。
- `scripts/nodo.ps1 seed-supply-pilot` 仅向开发库补齐匿名账号和虚构采购资料。已有账号继续使用原凭据，新密码只写本地账号文件。

## 人员档案接入

- `nodo_staff_import` 依赖 `nodo_base`、`hr` 和 `base_import`。部门层次用 `hr.department.parent_id`，岗位关联所在部门，员工在 Odoo 20 通过 `hr.version` 管理工作资料。用 `hr.employee` 的标准 ORM 写入和关联 `user_id`。
- 复用 `base_import.import._read_xlsx` 读第一张工作表。工号需用文本保存以保留前导零。CSV 使用 UTF-8，可带 BOM。确认表的首行字段和导入步骤见 [人员档案接入](手册/管理员/人员档案接入.md)。
- 以 `company_id` 和 `nodo_personnel_number` 作为稳定身份。目标公司、导入权限和已有登录名都在服务端校验。每次实际提交前按同一份文件重做预检。同一公司并发导入时更新公司行版本，由 Odoo 在快照过期时重试请求。
- 批次长期保留操作人、原文件名、目标公司和分类数量。结果页保留逐行预检摘要，上传内容在成功后清空。员工档案、用户权限组和个人开关分别维护。改动后运行 `scripts/nodo.ps1 test nodo_staff_import`。
